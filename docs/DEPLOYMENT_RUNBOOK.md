# Deployment and Release Runbook

## Purpose
This runbook defines the canonical release path for The Spirit Mask / Reading Nietzsche.

Repository: `LiveFromTheCasita/Nietzsche-SpiritMask`  
Production branch: `main`  
Hosting: Vercel  
Architecture: static HTML, shared CSS/JavaScript, no application framework or build dependency.

The governing rule is simple: substantial changes are reviewed on a scoped branch and pull request before they reach `main`. The Vercel project is connected to `main`, so merging an approved pull request is the normal production release action.

## Verified repository contract

The repository contains `vercel.json` with only URL-normalization redirects:

- `/index.html` -> `/`
- `/index` -> `/`

No framework build command, output-directory override, or custom deployment pipeline is defined in the repository.

The root README and project handoff both identify `main` as the production-connected branch and require scoped branch/PR review for substantial work.

The project is therefore treated as a Git-integrated Vercel static deployment unless the owner explicitly changes the Vercel project configuration.

## Standard release path

### 1. Start from the current production baseline

Before editing:

1. Confirm `main` is current.
2. Record the baseline commit SHA.
3. Read the canonical files in `docs/`.
4. Create one scoped branch for the work package.
5. Keep unrelated changes out of that branch.

Do not perform broad editorial or structural work directly on `main`.

### 2. Implement the bounded change

For content changes:

```sh
python3 scripts/build-index.py
node --check site.js
```

Commit regenerated `search-index.json` and `sitemap.xml` only when their generated bytes actually change.

Also perform any package-specific checks required by `docs/AGENT_INSTRUCTIONS.md`, including reading-progress migration checks when reading routes change.

Documentation-only changes do not require regenerating the search index or sitemap unless public site content is changed.

### 3. Review the branch before merge

For every substantial change:

- inspect the changed files;
- inspect representative changed pages in a browser or Vercel preview when a preview is available;
- verify relevant internal and external links;
- confirm translation/source labels for editorial changes;
- verify generated artifacts are current;
- ensure no unrelated files entered the diff.

High-risk editorial or scholarly changes require a second-pass review before merge.

A preview failure or missing preview is a stop condition for changes that alter public behavior or presentation. It may be documented rather than treated as a blocker for docs-only work.

### 4. Open a pull request

The pull request should state:

- work package;
- baseline SHA;
- branch;
- files changed;
- what changed and why;
- checks performed;
- whether generated files changed;
- whether a preview was inspected;
- unresolved questions or limitations;
- whether the change is safe to merge.

Do not merge while substantive review findings remain unresolved.

### 5. Merge to `main`

Once review passes, merge the scoped pull request into `main`.

Because `main` is the production-connected branch, this merge is the canonical release trigger for the existing Vercel project.

Do not create a replacement Vercel project for routine releases.

### 6. Verify production after merge

For any public-content or code release, verify after the production deployment becomes ready:

- homepage loads;
- at least one changed page loads;
- CSS and JavaScript load;
- search loads and returns a representative result if search data changed;
- navigation and changed anchors work;
- canonical production domain resolves to `https://thespiritmask.com/`;
- no obvious regression appears in the changed path.

For releases touching analytics, also perform the WP-17 account-side analytics checks.

Record the deployed commit SHA and the production verification result in the completion report.

## Release stop conditions

Do not continue to production, or treat the release as complete, when any of the following applies:

- the diff contains unrelated changes;
- required source or translation verification is incomplete;
- `scripts/build-index.py` produces unexplained generated changes;
- `node --check site.js` fails;
- an internal link, anchor, or reading-progress migration relevant to the change is broken;
- preview inspection reveals a public regression;
- the production deployment is not associated with the intended `main` commit;
- production verification fails.

Resolve the issue on the scoped branch and repeat review.

## Rollback expectations

### Preferred rollback: Git revert

For ordinary site releases, the safest default rollback is to revert the offending merge or commit in Git and allow the production-connected `main` branch to redeploy the known-good repository state.

Use this when:

- the released repository state itself is wrong;
- the fix should remain visible in Git history;
- generated assets need to return to the previous state.

After the revert deployment is ready, repeat the production verification checks.

### Vercel deployment rollback

Vercel can also roll production back to a prior deployment without rebuilding. This is appropriate as an emergency recovery action when the previous deployment is known good and immediate restoration matters.

A Vercel-only rollback does not change Git history. Therefore, after emergency rollback:

1. record which deployment was restored;
2. reconcile `main` so the repository again represents the intended production state;
3. do not leave Vercel production permanently diverged from `main`.

### Never use rollback as a substitute for diagnosis

After service is restored, identify the exact bad commit/change and document the corrective action.

## Deployment records

Every production-affecting work package should record:

- baseline SHA;
- pull request number;
- merge SHA;
- production deployment associated with that SHA when available;
- preview status;
- production verification status;
- rollback action, if any;
- unresolved operational limitations.
